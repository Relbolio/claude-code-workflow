Un workflow de développement avec Claude Code

Une suite de commandes qui fait passer chaque fonctionnalité par les mêmes étapes, de l'idée au merge. L'IA écrit le code, mais une autre IA le teste, et chaque étape laisse une trace que l'équipe peut relire.

L'idée centrale. Relire du code ne trouve presque aucun défaut d'exécution : ce sont les tests écrits par quelqu'un d'autre que l'auteur qui les trouvent. Tout le workflow est construit autour de ce constat, mesuré ci-dessous.

Le cycle d'une fonctionnalité

Spec→Contrats→Plan→Revue→Checklist de tests→Code→Tests par un agent distinct→Mutations→Porte de validation→Commit→Merge→Résumé

La planification du projet ne se fait qu'une fois. Le cycle, lui, se répète pour chaque fonctionnalité.

Pourquoi les tests sont écrits par un agent distinct

Un auteur qui teste son propre code teste ce qu'il a voulu écrire, pas ce qu'il a écrit. Il partage les mêmes angles morts, qu'il soit humain ou IA. Un agent sans le contexte d'écriture part de la spec, sans savoir ce que le code est censé faire de son point de vue : c'est cette ignorance qui le rend efficace.

Pour qu'un test compte, il faut aussi l'avoir vu échouer. L'agent casse volontairement le code une ligne à la fois (mutation) et vérifie que le test rougit. Un test qui reste vert quand on casse ce qu'il protège ne protège rien.

Exemple de prompt 
Tu es l'auteur des tests, distinct de celui qui a écrit ce code.
Exécute /write-feature-tests _plans/ma-feature.md.

À lire : la spec, le plan, la checklist _tests/ma-feature.md, puis git diff.

Règles :
- Base de données temporaire uniquement, jamais la base de travail.
- Les valeurs attendues viennent de la spec, pas du code.
- Ne modifie pas le code de production : classe chaque échec en défaut
  du produit ou hypothèse de test fausse, avec la preuve fichier:ligne.
- Joue la mutation témoin de chaque test bloquant, une par commande,
  en attendant sa fin, et vérifie la restauration avant la suivante.
- Ne commite rien.

Réponds avec : tests passants et échouants, mutations et résultats,
défauts produit, éléments non couverts.

Exécuter tout le workflow automatiquement

Le cycle complet peut tourner sans intervention, avec une seule consigne. Cela fait gagner beaucoup de temps, à condition que les bonnes conditions soient réunies.

Exemple de consigne 
Implémente cette fonctionnalité en suivant notre workflow :
spec → plan → revue → checklist de tests → implémentation → tests → commit → merge.
/write-feature-tests doit être exécutée par un agent distinct.
Merge local uniquement, ne pousse rien sans mon accord.
On peut lancer en confiance quand :
  • le besoin est clair et le périmètre borné ;
  • le projet a déjà des tests et une base de test jetable ;
  • le CLAUDE.md est à jour ;
  • le travail se fait sur une branche, et le merge reste local ;
  • « terminé » se mesure : build, tests, lint, en chiffres.
On garde la main quand :
  • il reste une décision produit ou métier à prendre ;
  • il s'agit d'un déploiement, ou d'un push qui en déclenche un ;
  • une migration peut détruire des données ;
  • on touche à des secrets ou à une publication ;
  • la validation n'a pas de tests sur lesquels s'appuyer.

L'automatisation ne retire pas l'humain, elle le déplace. La personne n'exécute plus chaque étape : elle fixe le périmètre, tranche les décisions et autorise la mise en ligne.

Garde-fous tirés de l'expérience
  • Une commande à la fois pendant les mutations. Sur un lot, des mutations lancées en parallèle ont faussé des résultats et sont restées un temps dans le code. Elles ont été rejouées seules.
  • Vérifier le rapport de l'agent en rouvrant ses preuves. Un agent qui s'arrête en route ne dit pas toujours où il en est : on contrôle l'état réel du code avant de reprendre.
  • Dire ce qui reste. Un résultat vert ne vaut que pour ce qui a été lancé. Le rapport final cite les chiffres réels et ce qui n'a pas été vérifié.

Ce qui a été mesuré

Sur un produit livré de bout en bout (12 modules, environ 50 000 lignes), voici ce qui a trouvé chaque défaut d'exécution :

Ce qui a trouvé le défautDéfauts
Suite d'intégration écrite par un auteur distinct10
Croisement des contrats back et front3
Bout en bout sur le parcours complet2
Passe en mode développement, français et anglais2
Relecture de code et revue de plan0

Les revues restent utiles : elles trouvent des erreurs de conception et de cohérence, avant le code. Sur un correctif récent lié à des paiements, deux revues indépendantes du plan ont soulevé 11 constats, puis les agents de test ont trouvé des défauts qu'elles n'avaient pas vus, dont un chemin qui déplaçait l'argent tout en répondant une erreur.

À garder en tête. Ces chiffres viennent de nos propres projets, sans groupe de comparaison : ce sont des observations, pas une preuve générale. Le cycle complet coûte aussi du temps et des jetons, jusqu'à 37 % des jetons d'un lot pour la seule revue du plan mesurée. Pour un petit changement à faible risque, on choisit une revue courte et une porte rapide.

Ce que ça change pour une équipe

  • Même méthode pour tous : la qualité dépend moins de la personne qui lance le travail.
  • Reprise facile : spec, plan, checklist et résumé restent dans le projet, chacun peut reprendre le sujet d'un autre.
  • Savoir partagé : un piège rencontré une fois entre dans CLAUDE.md, et s'applique à toute l'équipe.
  • Revue humaine mieux ciblée : le relecteur reçoit un verdict chiffré et peut se concentrer sur les choix, pas sur la mécanique.
  • Trace des décisions : on retrouve pourquoi un choix a été fait, utile pour un audit ou un incident.

Installer

git clone https://github.com/Relbolio/claude-code-workflow.git
cd claude-code-workflow
mkdir -p ~/.claude/commands ~/.claude/stacks ~/.claude/workflows
cp commands/* ~/.claude/commands/
cp stacks/* ~/.claude/stacks/
cp workflows/* ~/.claude/workflows/

Dans un projet, commencez par /claude-md, puis /create-feature-spec "ma fonctionnalité". Le détail de chaque étape est dans commands/WORKFLOW_GUIDE.md.
